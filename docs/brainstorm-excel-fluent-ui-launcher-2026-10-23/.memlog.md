- (direction) VSCode-style command palette with dual execution modes: 1) Desktop Excel COM mode (all 2,500+ native idMso commands + custom extension commands), 2) Excel Online mode (pure Office.js custom extension commands only, excluding COM commands)
- (question) Is executing original Excel COM commands done via PowerShell or cmd, or a persistent local bridge?
- (question) User raised concern: Kanata docs mention COM/virtual desktop can block the Kanata process. Do we need a split execution approach to avoid stacking/blocking the main Kanata thread?
- (decision) Kanata COM Execution must use a 'split way' (Worker Thread via mpsc channel). COM calls (ExecuteMso) can block, and if run on Kanata's main thread, they will freeze the user's keyboard. Must dispatch to a dedicated async/worker thread inside Rust.
- (insight by user) User accurately identified a critical Kanata architecture constraint: COM calls (like ExecuteMso) are blocking. To prevent freezing the system keyboard, Excel COM execution MUST use the 'split way' (subprocess or isolated worker thread) just like Kanata's run_subprocess_vd_op() does for Virtual Desktops.
- (insight by user) COM ExecuteMso fully supports native Excel Ctrl+Z Undo history. Office.js Excel.run typically clears the Undo stack.
